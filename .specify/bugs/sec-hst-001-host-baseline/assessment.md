# Bug Assessment: Unmeasured Host Hardening Baseline & Unverified Critical Claim for SEC-HST-001

- **Slug**: sec-hst-001-host-baseline
- **Created**: 2026-11-25
- **Source**: pasted text
- **Verdict**: valid
- **Severity**: high

## Report (verbatim or summarized)

> `baseline_pre.json` sigue siendo `illustrative` y `baseline_post.json` es `captured_config_verification`, no una captura real del host; el antes/después de SSH/UFW es una plantilla y tests de texto, no la salida de `verify_hardening.sh` en un host. Ejecuta `capture_baseline.sh`/`verify_hardening.sh` en staging o producción y adjunta la salida medida, o elimina SEC-HST-001 de los críticos y documenta el riesgo.

## Symptom

The OWASP audit deliverables certify `SEC-HST-001` (Host SSH & Firewall Hardening) as a `CRITICAL` vulnerability with `verification_status: "VERIFIED_RESOLVED"`, counting it as 1 of 3 resolved critical vulnerabilities across the audit matrix, executive summary, remediation proof, and Spanish cybersecurity report. However, the committed evidence is backed only by declarative repository templates (`infra/host/sshd_config.hardened`, `infra/host/ufw_setup.sh`, `docker-compose.yml`), static text-matching pytest assertions (`test_host_hardening_verification.py`), an illustrative pre-remediation JSON (`"provenance": "illustrative"`), and a synthetic post-remediation JSON (`"provenance": "captured_config_verification"`) generated by a script (`capture_baseline.sh`) that hardcodes its JSON payload rather than parsing live host probes or recording actual staging/production output from `verify_hardening.sh`.

Expected behavior: Either (a) `capture_baseline.sh` and `verify_hardening.sh` are executed against a real staging or production Linux host and their measured outputs (`"provenance": "measured_host_capture"` and strict-mode `verify_hardening.sh` stdout) are attached as evidence, or (b) `SEC-HST-001` is removed from the resolved `CRITICAL` count (or downgraded/reclassified as an unverified host-level deployment requirement / residual operational risk) and documented transparently across the matrix, proof documents, and contract tests.

2. Inspect `infra/host/baseline_post.json:2-6`: `"profile_id"` is `"HOST-BASE-POST-trackflow-ci"`, `"provenance"` is `"captured_config_verification"`, and `"hostname"` is `"trackflow-ci"`, indicating an offline/CI configuration snapshot rather than a live staging or production host measurement.

## Root Cause Hypothesis

Because the repository and development/test environment run locally (on Windows / CI without SSH access to a live Linux staging or production server), the previous remediation pass satisfied host hardening requirements by creating declarative hardening artifacts (`sshd_config.hardened`, `ufw_setup.sh`, `permissions_setup.sh`, loopback bindings in `docker-compose.yml`) and a baseline script (`capture_baseline.sh`) that falls back to `"captured_config_verification"` when Linux socket/firewall tools (`ss`, `ufw`) are unavailable. However, `SEC-HST-001` was still elevated to a `CRITICAL` / `VERIFIED_RESOLVED` finding in the OWASP matrix and executive reports, conflating declarative repository configuration templates with verified runtime host remediation. Confidence: high.

## Proposed Remediation

**Preferred (Option B if no live staging/production Linux host is accessible from the repository environment)**:
1. **Remove `SEC-HST-001` from the Resolved Criticals & Document Operational Risk**:
   - In `specs/036-owasp-audit-hardening/audit/owasp_audit_matrix.json`, either remove `SEC-HST-001` from the resolved critical findings list or reclassify `SEC-HST-001` from `CRITICAL` / `VERIFIED_RESOLVED` to a non-critical operational control / residual risk (or `IN_PROGRESS` / `MITIGATED` with `HIGH`/`MEDIUM`/`INFORMATIONAL` severity, or remove it from the code-verified criticals count), explicitly stating that repository templates (`sshd_config.hardened`, `ufw_setup.sh`, `docker-compose.yml` loopback bindings) are verified in CI (`--template-check`), while live OS enforcement on staging/production hosts remains an operational deployment prerequisite and residual risk until `capture_baseline.sh` and `verify_hardening.sh` are run on target infrastructure.
   - Update the resolved Critical findings count from `3` to `2` (`SEC-BK-005` and `SEC-AG-002`) in `specs/036-owasp-audit-hardening/audit/critical_remediation_proof.md`, `specs/036-owasp-audit-hardening/audit/executive_summary.md`, `docs/cybersecurity-analysis/owasp-top10-security-audit-report.md`, and `services/api/tests/unit/test_security_audit_matrix.py`.
   - Document the residual host risk and the exact runbook commands (`sudo bash infra/host/capture_baseline.sh` and `sudo bash infra/host/verify_hardening.sh`) required during staging/production provisioning in `critical_remediation_proof.md` (Section 3: Residual Risk & Verification Sign-Off) and `docs/cybersecurity-analysis/owasp-top10-security-audit-report.md` (Section 6 / Section 7.4).
2. **Make `capture_baseline.sh` Actually Parse Live Host State**:
   - Update `infra/host/capture_baseline.sh` so that when executed on a Linux host, it dynamically parses `sshd -T` (or `/etc/ssh/sshd_config`), `ss -ltnH`, and `ufw status` to populate `ssh_config`, `listening_ports`, and `firewall_rules` from measured outputs instead of emitting hardcoded JSON arrays, and fails (or requires an explicit `--offline-template` flag) rather than silently fabricating a post-remediation host capture when host tools are absent.

**Alternative (Option A — if a staging or production Linux host is available)**:
- Improve `infra/host/capture_baseline.sh` to parse real `ss -ltnH`, `ufw status`, `docker ps`, `iptables -S DOCKER-USER`, and `sshd -T` outputs.
- Execute `capture_baseline.sh` before and after applying `sshd_config.hardened`, `ufw_setup.sh`, and `permissions_setup.sh` on the target staging/production Linux host, and commit the measured `baseline_pre.json` and `baseline_post.json` (`"provenance": "measured_host_capture"`).
