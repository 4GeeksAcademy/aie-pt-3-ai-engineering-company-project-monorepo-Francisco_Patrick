## 1. LangGraph StateGraph Architecture & Expanded Minimal State Schema

### Decision
Maintain an explicit, minimal Python `TypedDict` schema named `AgentState` containing only the structured fields needed for multi-source reasoning, operational tool execution, static knowledge retrieval, fallback tracking, and queryable tracing:
- `query`: `str` (sanitized input question)
- `language`: `str` (target language code, defaults to `"en"`)
- `top_k`: `int` (retrieval depth, defaults to `3`)
- `min_score`: `float` (calibrated similarity threshold, defaults to `0.62`)
- `selected_sources`: `List[str]` (ordered list of planned data sources selected by autonomous routing at intake, subset of `["ticket_tool", "inventory_tool", "rag"]` in canonical sequence)
- `sources_consulted`: `List[str]` (chronological list of data sources actually consulted during the run)
- `ticket_tool_input`: `Optional[TicketToolInput]` (extracted ticket lookup/filter parameters when `ticket_tool` is selected)
- `ticket_tool_output`: `Optional[TicketToolOutput]` (typed result from `SupportTicketToolPort`)
- `inventory_tool_input`: `Optional[InventoryToolInput]` (extracted product/SKU query parameters when `inventory_tool` is selected)
- `inventory_tool_output`: `Optional[InventoryToolOutput]` (typed result from `InventoryStockToolPort`)
- `contexts`: `List[RetrievedContext]` (retrieved static policy chunks satisfying `min_score`)
- `fallback_triggered`: `bool` (flag indicating whether an operational tool degraded, timed out, or returned `not_found`)
- `fallback_messages`: `List[str]` (honest inability-to-confirm notice(s) generated by `tool_fallback_node`)
- `answer`: `str` (synthesized response, hybrid partial response, honest fallback message, or standardized policy refusal)
- `is_refusal`: `bool` (flag indicating whether the inquiry was refused as out-of-scope, empty, or disallowed write mutation)
- `sources`: `List[SourceCitation]` (provenance metadata for verified static policy documents)
- `trace_id`: `str` (unique execution run identifier)
- `node_history`: `List[str]` (ordered sequence of executed node identifiers)
- `step_latencies`: `Dict[str, float]` (per-node duration in milliseconds)
- `node_outputs`: `Dict[str, Dict[str, Any]]` (structured summary payload per visited node)
- `error`: `Optional[str]` (sanitized error message if an unhandled fault occurs)

Unbounded raw conversational message history (`List[BaseMessage]`) remains strictly excluded (FR-001).

### Rationale
- **Minimal & Inspectable (FR-001)**: Keeps state token-lean, strongly typed, and serializable across LangGraph `MemorySaver` checkpoints without accumulating multi-turn chat bloat.
- **Explicit Source Separation (FR-004, FR-020)**: `ticket_tool_output`, `inventory_tool_output`, and `contexts` occupy distinct typed slots so `generation_node` and `tool_fallback_node` can synthesize grounded answers or partial degradation notices deterministically without ever calling external services directly.

### Alternatives Considered
- *Untyped generic `tool_results: List[Any]`*: Rejected because combining heterogeneous ticket and inventory records into an untyped list weakens static type safety (Constitution Principle III) and blurs single-responsibility boundaries (FR-020).
- *LangChain `MessagesState` with ReAct `ToolNode` loop*: Rejected because an unconstrained cyclic tool loop can re-invoke tools arbitrarily, obscuring deterministic node ordering (`ticket_tool` → `inventory_tool` → `rag`) and complicating build-time structural verification.

## 2. Single-Responsibility Operational Tool Contracts & Real Data Integration

### Decision
Implement two separate, strictly read-only operational tools backed by TrackFlow's real persistence layers (`IncidentService` over TinyDB `db.json` and `InventoryService` over SQLite/SQLModel `inventory.db`), with optional HTTP client transport when `AGENT_API_BASE_URL` is configured:

1. **Support Ticket Query Tool (`SupportTicketToolPort` / `IncidentSupportTicketToolAdapter`)**:
   - **Input Contract (`TicketToolInput`)**:
     - `ticket_id: Optional[str]` (exact incident ID such as `inc_...`, `INC-001`, or legacy ID)
     - `status: Optional[str]` (`open`, `in_progress`, `resolved`, `discarded`)
     - `category: Optional[str]` (`delay`, `damage`, `billing`, `stock`, `system`, `other`)
     - `origin: Optional[str]` (`customer`, `warehouse`, `carrier`, `partner`, `internal`)
     - `branch: Optional[str]` (e.g., `central`, `zaragoza`, `los_angeles`, `valencia`)
     - `limit: int = 20` (capped at 20 max per FR-016)
   - **Output Contract (`TicketToolOutput`)**:
     - `status: Literal["success", "not_found", "timeout", "error"]`
     - `records: List[TicketRecordDTO]` (up to 20 matching records ordered most recent `updated_at` / `created_at` first, containing `id`, `title`, `description`, `status`, `category`, `origin`, `branch`, `created_at`, `updated_at`)
     - `total_matched: int` (total records matching criteria prior to the 20-record slice)
     - `latency_ms: float`
     - `error_message: Optional[str]` (sanitized failure reason when `status` is `not_found`, `timeout`, or `error`)
   - **Data Source**: Queries `IncidentService.get_incident_by_id()` (plus `find_by_legacy_id()` / case-normalized ID lookup) or `IncidentService.list_all_incidents(status=..., origin=..., branch=..., category=...)`. Also supports optional HTTP `GET /api/incidents/{id}` and `GET /api/incidents` via `httpx.Client` when configured.

2. **Inventory Stock Query Tool (`InventoryStockToolPort` / `InventoryStockQueryToolAdapter`)**:
   - **Input Contract (`InventoryToolInput`)**:
     - `product_id: Optional[int]` (numeric SKU primary key ID)
     - `sku: Optional[str]` (alphanumeric SKU code, e.g., `TF-1001`, `SKU-001`)
     - `search_query: Optional[str]` (case-insensitive substring filter over product `name` or `sku`, or `"low_stock"` filter)
     - `low_stock_only: bool = False`
     - `limit: int = 20` (capped at 20 max per FR-018)
   - **Output Contract (`InventoryToolOutput`)**:
     - `status: Literal["success", "not_found", "timeout", "error"]`
     - `records: List[InventoryRecordDTO]` (up to 20 matching records ordered by relevance/ID, containing `id`, `sku`, `name`, `description`, `stock`, `min_threshold`, `is_low_stock`, `warehouse_id`)
     - `total_matched: int`
     - `latency_ms: float`
     - `error_message: Optional[str]`
   - **Data Source**: Queries `InventoryService.get_product_by_id()` or `InventoryService.list_products()` directly against `SQLModelInventoryRepository` (`inventory.db`). Note: because `GET /inventory/products` in the HTTP router enqueues an async Celery task (HTTP 202), in-process `InventoryService` (and `GET /inventory/products/{id}` for single-ID HTTP calls) provides synchronous real-time stock calculation within the 4.0s deadline. Since the `SKU` table stores `sku`, `name`, `warehouse_id`, and `low_stock_threshold`, `InventoryRecordDTO` maps `stock = current_stock`, `min_threshold = low_stock_threshold`, and derives `description` (`f"{product.name} (Warehouse: {product.warehouse_id})"`) when no separate description column exists.

### Rationale
- **Real Data Compliance (FR-017, FR-018, SC-005)**: Directly reads TrackFlow's live TinyDB and SQLModel data stores—zero mocked arrays or hardcoded production responses.
- **Strict Read-Only Contract (FR-019)**: Neither `SupportTicketToolPort` nor `InventoryStockToolPort` exposes any creation, status mutation, or order dispatch method.
- **20-Record Cap + `total_matched` (Clarification Session 2026-11-18)**: Prevents state bloat when a filter matches hundreds of incidents or products while preserving exact cardinality visibility for synthesis.
- **Environment-Driven Authentication (FR-021)**: When using in-process service ports, calls execute within the trusted service boundary; when configured for external HTTP transport (`AGENT_API_BASE_URL`), optional bearer credentials are loaded exclusively from `os.getenv("AGENT_INTERNAL_API_TOKEN")` and never hardcoded.

### Alternatives Considered
- *Calling `GET /inventory/products` via HTTP and polling Celery `/api/v1/tasks/{id}`*: Rejected because Celery polling introduces multi-second queue variance and requires an active Redis/Celery worker process for basic stock reads, whereas `InventoryService.list_products()` reads the real `inventory.db` synchronously in < 10ms.
- *Single unified `operational_database_tool`*: Rejected because FR-020 explicitly mandates separate single-responsibility tools and graph nodes for support tickets and inventory stock.

## 3. Autonomous Intent Routing & Canonical Multi-Source Execution Order

### Decision
At `intake_node`, after input sanitization and length validation (`>= 3` chars), execute an autonomous intent classifier and parameter extractor (`classify_and_plan_query(query)`) that inspects the natural-language question without requiring user-provided source hints:

1. **Write/Mutation Guardrail Check (Edge Case: Prompt Injection / Mutation Refusal)**:
   - Detects requests attempting to create, open, update, modify, close, resolve, discard, or delete a ticket, or add/remove/update inventory stock quantities (e.g., `"Close ticket INC-001"`, `"Delete incident inc_123"`, `"Update stock for SKU TF-1001 to 500"`).
   - Immediately flags `is_refusal = True` with an explicit read-only refusal notice and routes `intake` → `refusal`.

2. **Autonomous Source Selection (`selected_sources`)**:
   - **Ticket Intent (`"ticket_tool"`)**: Triggered when the inquiry references support ticket/incident identifiers (e.g., `INC-\d+`, `inc_[a-z0-9]+`, `ticket #...`, `incident #...`) or live incident operational status/listings (e.g., `"open incidents"`, `"critical incidents"`, `"status of ticket"`, `"incidents from warehouse"`, `"tickets in zaragoza branch"`). Extracts `TicketToolInput` (`ticket_id`, `status`, `category`, `origin`, `branch`).
   - **Inventory Intent (`"inventory_tool"`)**: Triggered when the inquiry references product SKUs (e.g., `SKU`, `TF-\d+`, `PRD-\d+`, `product ID \d+`) or live warehouse stock/availability levels (e.g., `"how many units"`, `"in stock"`, `"stock level"`, `"low stock products"`, `"inventory availability for"`). Extracts `InventoryToolInput` (`product_id`, `sku`, `search_query`, `low_stock_only`).
   - **Static Policy / Documentation Intent (`"rag"`)**: Triggered when the inquiry asks about company policies, return windows, shipping fee responsibilities, SLA tiers, storage pricing rates, discount approvals, claims, or general questions not exclusively answered by a live ticket/SKU lookup—or whenever no operational tool matches (so out-of-distribution topics still pass through `retrieval_node` and fail the `0.62` similarity threshold cleanly to `refusal_node`).
   - **Canonical Ordering (Clarification Session 2026-11-18 & FR-025)**: Whenever multiple sources are selected (hybrid inquiry), `selected_sources` is always ordered canonically as:
     `["ticket_tool", "inventory_tool", "rag"]` (filtered to the active subset).

3. **Deterministic Graph Topology & Conditional Edges**:
   - `START` → `intake`
   - `route_after_intake(state)`:
     - If invalid/empty query or write-mutation attempt (`is_refusal == True`): → `"refusal"`
     - Else returns the first planned stage in `selected_sources`: `"ticket_tool"` | `"inventory_tool"` | `"retrieval"` (where `"rag"` maps to node `"retrieval"`).
   - `route_after_ticket_tool(state)`:
     - If `"inventory_tool"` in `selected_sources`: → `"inventory_tool"`
     - Else if `"rag"` in `selected_sources`: → `"retrieval"`
     - Else if `ticket_tool_output.status != "success"`: → `"tool_fallback"`
     - Else: → `"generation"`
   - `route_after_inventory_tool(state)`:
     - If `"rag"` in `selected_sources`: → `"retrieval"`
     - Else if any consulted operational tool had `status != "success"` (`fallback_triggered == True`): → `"tool_fallback"`
     - Else: → `"generation"`
   - `route_after_retrieval(state)`:
     - If any consulted operational tool had `status != "success"` (`fallback_triggered == True`): → `"tool_fallback"`
     - Else if `len(qualified_contexts) > 0` or any operational tool succeeded: → `"generation"`
     - Else (pure RAG query with 0 chunks `>= 0.62`): → `"refusal"`
   - `route_after_tool_fallback(state)`:
     - If `len(qualified_contexts) > 0` or at least one operational tool succeeded (partial hybrid success): → `"generation"`
     - Else (all requested operational tools failed/not_found and no RAG context exists): → `END` (since `tool_fallback_node` already populated the honest fallback `answer`).

### Rationale
- **Canonical Sequence Guarantee (FR-025)**: By structuring the conditional edges along the topological order `ticket_tool` → `inventory_tool` → `retrieval` → `tool_fallback` → `generation`, every hybrid query is guaranteed to execute operational tools before static RAG retrieval, and to record tool fallback before final synthesis.
- **Graceful Partial Answer on Hybrid Degradation (Clarification Session 2026-11-18 & FR-023)**: In a hybrid query (e.g., `"What is the status of ticket INC-999999 and what is our standard return policy?"`), `ticket_tool` executes first and records `status="not_found"` (`fallback_triggered=True`), then transitions to `retrieval` (which retrieves the 30-day return policy), then transitions to `tool_fallback` (which records the honest inability-to-confirm notice for `INC-999999`), and finally transitions to `generation` (which combines the verified 30-day return policy answer with the honest ticket fallback notice).
- **Zero Hallucination on Pure Tool Failure**: In a pure tool query where the ticket/product is missing or the service times out (`selected_sources=["ticket_tool"]`), `ticket_tool` routes directly to `tool_fallback`, which formats the honest inability-to-confirm response (`"I couldn't confirm the status of ticket 'INC-999999' right now because no matching incident record was found."` or `"I couldn't confirm the status of that ticket right now due to a service timeout."`) and terminates at `END` without invoking LLM generation.

### Alternatives Considered
- *Aborting hybrid queries immediately when a tool fails*: Rejected because the spec clarification explicitly requires graceful partial answers: record the tool fallback, still execute `rag`, and return the verified policy answer alongside the honest inability-to-confirm notice.

## 4. Explicit Numerical Timeouts & Controlled Error Recovery (`tool_fallback`)

### Decision
1. **Numerical Timeout Enforcement (`4.0` seconds default, configurable via `AGENT_TOOL_TIMEOUT_SECONDS`)**:
   - Every operational tool invocation (`SupportTicketToolPort.query_tickets` and `InventoryStockToolPort.query_inventory`) executes within a bounded timeout wrapper (using a dedicated `ThreadPoolExecutor` `future.result(timeout=timeout_seconds)` and `httpx.Timeout(timeout_seconds)` when using HTTP transport).
   - If execution exceeds `timeout_seconds` (default `4.0`s) or raises `TimeoutError` / `httpx.TimeoutException`, the adapter catches it immediately and returns `TicketToolOutput(status="timeout", ...)` or `InventoryToolOutput(status="timeout", ...)` with `latency_ms` recorded and a sanitized error description.
2. **Service Exception & Missing Record Handling**:
   - If the underlying service/repository raises an unexpected exception (e.g., database locked, connection refused, HTTP 5xx), the adapter catches it and returns `status="error"` with a sanitized message (never exposing raw tracebacks).
   - If the query completes cleanly but matches 0 records (`len(records) == 0`), the adapter returns `status="not_found"`.
3. **Explicit `tool_fallback_node`**:
   - Inspects `ticket_tool_output` and `inventory_tool_output`.
   - Appends `"tool_fallback"` to `node_history` and records step latency.
   - Generates deterministic, honest inability-to-confirm notices (`fallback_messages`) tailored to the specific tool and failure mode (`not_found`, `timeout`, `error`), ensuring zero invented ticket statuses, dates, categories, or stock numbers.
   - If no static `contexts` and no successful tool outputs exist, sets `state["answer"]` directly to the combined honest fallback message (`is_refusal=False`, `fallback_triggered=True`) and finishes. If partial context exists (e.g., `rag` succeeded in a hybrid query), passes `fallback_messages` to `generation_node` so the final answer includes both the verified policy response with citations and the honest inability-to-confirm notice.

### Rationale
- **Guarantees SC-002 & SC-003**: No tool call can ever block the agent workflow beyond the configured `4.0`s timeout, and 100% of degraded or missing-record tool lookups traverse `tool_fallback` and produce honest responses.

## 5. Multi-Source Execution Tracing & Checkpointing

### Decision
Extend `AgentTrace`, `AgentQueryResult`, and the presentation DTOs (`AgentQueryResponseSchema`, `AgentTraceResponseSchema`) with explicit multi-source provenance while maintaining 100% backward compatibility with Part 1 fields:
- `sources_consulted: List[str]`: Ordered list of data sources consulted during the run (e.g., `["rag"]`, `["ticket_tool"]`, `["inventory_tool"]`, `["ticket_tool", "rag"]`).
- `fallback_triggered: bool`: Whether `tool_fallback` was activated during the run.
- `tool_calls: List[Dict[str, Any]]`: Ordered summary of operational tool invocations (`tool_name`, `input_summary`, `status`, `matched_count`, `total_matched`, `latency_ms`).
- Existing fields (`trace_id`, `query`, `node_sequence`, `step_latencies`, `total_duration_ms`, `is_refusal`, `final_answer`, `source_count`, `node_outputs`, `checkpoints`) remain unchanged in type and meaning.

### Rationale
- **Satisfies FR-008, FR-025, SC-001**: Engineers and automated evaluation tests can inspect `trace.sources_consulted`, `trace.node_sequence`, and `trace.tool_calls` to verify which data sources were queried and in what exact chronological order.
- **Backward Compatibility (Constitution Principle II)**: All new response fields have safe defaults so existing consumers and Part 1 tests continue to work without modification.

## 6. Automated Evaluation Suite Expansion (Part 1 + Part 2 Gates)

### Decision
Preserve all 4 Part 1 evaluation scenarios (`EVAL-001` through `EVAL-004`) in `tests/pipelines/test_support_agent_evaluation.py` and add Part 2 evaluation scenarios covering FR-026 and FR-027:
- **EVAL-005 (Autonomous Operational Tool Routing — Live Support Ticket)**:
  - Query: `"What is the current status and category of support ticket INC-001?"` (seeded deterministically into the test TinyDB incident store).
  - Asserts: `sources_consulted == ["ticket_tool"]`, `node_sequence == ["intake", "ticket_tool", "generation"]`, `"retrieval"` NOT in `node_sequence` (not resolved via RAG), `fallback_triggered is False`, and final answer accurately reports the live status, category, origin, and branch of `INC-001`.
- **EVAL-006 (Autonomous Static RAG Routing vs Operational Tools)**:
  - Query: `"What is TrackFlow's standard return window and who covers return shipping costs?"`
  - Asserts: `sources_consulted == ["rag"]`, `node_sequence == ["intake", "retrieval", "generation"]`, neither `"ticket_tool"` nor `"inventory_tool"` is visited, and answer is grounded in `returns-policy` (30 days).
- **EVAL-007 (Autonomous Inventory Tool Routing — Live Product Stock)**:
  - Query: `"How many units of SKU TF-1001 are currently in stock?"` (seeded deterministically into the test SQLModel inventory store).
  - Asserts: `sources_consulted == ["inventory_tool"]`, `node_sequence == ["intake", "inventory_tool", "generation"]`, `"retrieval"` and `"ticket_tool"` NOT visited, and final answer reports exact live stock units and low-stock threshold status.
- **EVAL-008 (Honest Fallback Recovery on Missing Ticket / Unavailable Service)**:
  - Sub-scenario A (Missing Record): Query `"What is the status of support ticket INC-999999?"` → Asserts `node_sequence == ["intake", "ticket_tool", "tool_fallback"]`, `fallback_triggered is True`, answer honestly states inability to confirm/find `INC-999999` without inventing status or dates.
  - Sub-scenario B (Simulated Tool Timeout / Unavailable Service): Inject a delayed/unavailable `SupportTicketToolPort` exceeding the numerical timeout → Asserts execution completes within bound, traverses `"tool_fallback"`, and honestly reports `"I couldn't confirm the status of that ticket right now"`.
- **EVAL-009 (Hybrid Multi-Source Execution & Graceful Partial Fallback)**:
  - Query combining live ticket + static policy: `"What is the status of ticket INC-001, and what is TrackFlow's standard return window?"` → Asserts canonical execution sequence `["intake", "ticket_tool", "retrieval", "generation"]` and `sources_consulted == ["ticket_tool", "rag"]`.
  - Hybrid with missing ticket (`INC-999999` + return policy) → Asserts sequence `["intake", "ticket_tool", "retrieval", "tool_fallback", "generation"]`, returning the verified 30-day return policy alongside the honest inability-to-confirm notice for `INC-999999`.

### Rationale
- **Satisfies FR-009 through FR-012 and FR-026, FR-027, SC-004, SC-007**: All evaluations run deterministically in a single `pytest tests/pipelines/` invocation without external network dependencies.
